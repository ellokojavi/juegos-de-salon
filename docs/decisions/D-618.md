## D-618 · The merge queue runs end-to-end once per PR: a behind PR's run is cancelled and only `tests` lets it in line
**Date:** 2026-11-24 · **Status:** current · **Relation:** amends D-586 · **Topics:** agents
**Context:** With the queue of D-586 a PR joined the line only after `tests` and `end-to-end` passed, and then ran `end-to-end` again after the queue merged main into it. So every PR paid two `end-to-end` rounds, and the first one, on a main it could no longer merge into, kept running while the PR waited behind. One `end-to-end` run spreads over 18 groups and nearly fills the account's ~20 runners, so those stale runs slowed down the run of the PR whose turn it was. On 2026-11-24 six PRs took about 15–30 minutes each to clear. The owner asked for both changes.
**Decision:** (1) On each step the queue cancels the running `end-to-end` of every PR in the line's reach (auto-merge on, not 🔴, from this repo) that is behind main. (2) A behind PR joins the line when `tests` passed and `end-to-end` did not fail: still running, never run or cancelled all count. A real `end-to-end` failure still keeps it out until its session fixes it. A cancelled run is not red anywhere (`wait-pr.mjs`, `pending.mjs`, `processes.mjs`): a newer push or the queue's update always runs it again.
**Why:** `end-to-end` runs once per PR, on the main it merges into, and the runners go to the PR whose turn it is. Coverage is unchanged: every PR still merges only after a full `end-to-end` on today's main (D-216).
**Consequences:** A PR whose `end-to-end` breaks finds out at its turn rather than before, and that turn is lost for the line (the queue moves on as soon as the check is red). With no earlier passing run, the run after the update covers the PR's whole scope rather than D-612's intersection, which replaces the earlier first run. The queue's token needs to be allowed to cancel workflow runs; a refusal is logged and the queue goes on as before.
