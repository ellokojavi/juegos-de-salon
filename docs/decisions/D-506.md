## D-506 · From merge to live in minutes: narrow by the PR head, no run-wide queue, retry 5xx, no sealed version
**Date:** 2026-10-29 · **Status:** current · **Relation:** amends D-496 (the narrowed run diffs against the PR head, not the first parent), D-302 (publish.yml's queue) and D-51 (the seal) · **Topics:** publishing, tests, readme
**Context:** on 2026-10-29 (UTC) the owner saw changes take hours to go live. Measured with `gh run list/view`: #985's Publish waited 11 minutes for runners, then its "narrowed" end-to-end run (D-496) ran all 18 groups (20 minutes) because it diffed the merge against its first parent, which is the PR's whole diff, already tested on the PR; then the Pages deploy failed with a 502 after 39 minutes. Behind it, the workflow-wide `concurrency: pages` queue kept #987's run waiting 23 minutes without starting and cancelled #993's. Meanwhile #985, #987 and #989 kept going DIRTY: every seal rewrote the second line of `docs/facts.json`, `"version"`, which changes with every changelog entry, so each merge forced the others to re-merge and rerun ~30 minutes of checks.
**Decision:** (1) `already-tested.mjs` passes the merge's second parent (the PR head that passed) as `base`: publishing retests smoke plus the scripts reached by what main gained since that head, not the PR's own files again. (2) publish.yml has no workflow-wide queue: tests and end-to-end start at once; only `rules` and `publish` each wait in their own group, and each first asks whether its commit is still main's head; an overtaken run publishes nothing and its report says the newer merge publishes it. (3) The Pages deploy is retried twice (after 1 and 2 minutes) only when it failed with a 5xx, or when an older commit's deployment is stuck in progress, which the run then cancels first (2026-10-29: #985's deployment never ended after its 502 and blocked every later one) (`tools/release/pages-5xx.mjs` reads the failed step's annotations). (4) `readme.py seal` no longer writes `version` into `docs/facts.json` (`check` already ignored it).
**Why:** each of the four cost tens of minutes on the same night, and none bought any safety: the PR's files were tested on the PR, the queue only serialized work that can run in parallel, a 502 is GitHub's and goes away, and the sealed version was never compared.
**Alternatives discarded:** a `merge=union` or custom merge driver for `docs/facts.json` (GitHub's mergeability ignores custom drivers, and a union of JSON is not JSON); generating the seal at publish time (the seal is the record that a person reread the prose, so it must be committed by that person); skipping the end-to-end run on main altogether (smoke still catches two PRs that break each other).
**Consequences:** a typical merge goes live in about 8 to 12 minutes (runner wait, tests, smoke plus a few groups, deploy) instead of 40 or more; a 5xx costs 1 to 3 minutes instead of the whole run. Two PRs that both seal now conflict only when they change the same fact.
