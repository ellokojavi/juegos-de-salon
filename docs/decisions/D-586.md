## D-586 · A homemade merge queue: one PR at a time is brought up to date before it merges (trial)
**Date:** 2026-11-18 · **Status:** current · **Relation:** extends D-216 (auto-merge) and D-580 (sync-pr) · **Topics:** agents
**Context:** About 33 PRs merge a day from many sessions. `main` did not require branches up to date, so a PR merged tested against a stale main, and two PRs without a git conflict that passed alone broke main together (#1567). The repo is personal, so GitHub's merge queue is not offered.
**Decision:** The owner approved a trial. `main` requires branches up to date (strict), so auto-merge, still the merger, never merges a PR behind main. `merge-queue.yml` (`tools/agents/merge-queue.mjs step`, one run at a time, on check completion, push to main and every 15 minutes) updates only the head of the line: the open PR with auto-merge on the longest whose `tests` and `end-to-end` passed but that is behind main, by merging main in (update-branch, then `sync-pr.mjs` for generated-file conflicts; never a rebase). While that PR's checks run, the rest wait. A real conflict gets one comment and is skipped; a 🔴 PR waiting for the owner is skipped until approved (`approve.mjs` turns on auto-merge when the PR is behind). The pushes need the `MERGE_QUEUE_TOKEN` secret, because the workflow token wakes no workflow. Off switch: repo variable `MERGE_QUEUE=off` plus strict off (docs/MERGING.md).
**Why:** Testing each PR on the main it merges into is the only way to catch the pair that breaks together; one update at a time avoids an avalanche of re-runs.
**Consequences:** A PR may wait for others' checks before merging. `merge-queue.mjs report` measures the trial against the same-length period before it (merges per day, main red, queue wait, extra runs); the owner keeps or drops it on those numbers.

**The evaluation (2026-11-25, a scheduled task).** It runs `merge-queue.mjs report --since 2026-11-19`
against the baseline and decides one of three, writing the numbers here:

- **Remove** (off switch, strict back off): main went red as often as before, or merges per day fell.
- **Keep as it is**: main red less often, and the queue wait stayed short: p90 ≤ 30 min and max ≤ 90 min
  on all but at most two days.
- **Build on it**, in this order, each only if the one before was not enough:
  1. *The shortcut*: merge without re-testing a PR when what entered main since its last pass touches
     no test its files reach and it touches none theirs reach (the TEST-SCOPE map, D-391). Worth it if
     at least a third of the queue's branch updates were for such disjoint pairs.
  2. *Testing in groups*: main + the ready PRs on one temporary branch, one test run, all merge if green,
     split in halves to find the culprit if red (as GitHub's merge queue does). Worth it only if, with
     the shortcut, p90 wait is still over 30 min, or max over 90 min on three or more days. Otherwise
     it is dropped and this decision says so.
