## D-469 · The rules check a room's shape and keep a bucket's clock moving forward
**Date:** 2026-10-27 · **Status:** current · **Relation:** completes D-41 and D-321 · **Topics:** rooms
**Context:** D-41 capped rooms per phone in the app and left tighter rules for later. D-321 made the
app write a new room and its cleanup note in one write. The rules now also check the shape of what
a room holds.
**Decision:**
- A bucket's `lastAt` only moves forward.
- `config`, `players/<seat>` and `messages/<id>` take only the fields the games send (`$other: false`),
  each with a type and a generous size cap; nested values (a move's cells, a fleet's layout, sealed
  hands, Timeline's skipped cards) only as deep and with the keys the games write.
- `feedback.mjs sync` uploads at most 20 new reports per pass, oldest first, and warns when some wait.
- The monthly download alert stays a manual console step (`firebase/README.md`): the service account
  key is for the database, not for configuring Google Cloud.
- A room's `createdAt` is accepted only when the same write notes the room in today's cleanup bucket
  or a neighboring day's (`cleanup/days/<day>/rooms/<CODE>`; the neighbors cover a phone whose clock
  estimate falls on the other side of midnight UTC), and a bucket's `lastAt` is written only on
  today's bucket, yesterday's or tomorrow's. Added in a second PR, after the Realtime Database
  emulator (v4.11.2) confirmed how the rules turn the day number into a bucket key (`"20753"`, no
  decimals) and accepted the write `roomCreation` makes.
**Why:** cleanup and storage on the free plan depend on every room being noted and every bucket
closing; a shape check costs nothing at play time.
**Consequences:** a game that sends a new message field, or a new config setting, must add it to
`firebase/database.rules.json` in the same PR, or its rooms break; `firebase/room-limits.test.mjs`
covers the shapes each game sends today.
