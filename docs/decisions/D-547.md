## D-547 · 🔥 Popular is recomputed every Monday by a scheduled workflow, not by the processes round
**Date:** 2026-11-08 · **Status:** current · **Relation:** amends D-361 (the weekly refresh was a step of the processes round) · **Topics:** home, agents
**Context:** the owner wants the 🔥 Popular label on the three most popular games to stay fresh on a fixed
weekly cadence, set and removed automatically, so it points players to games the crowd likes beyond the
new ones. Until now the count ran only when the processes round remembered it was due.
**Decision:** `.github/workflows/popularity.yml` runs every Monday at 12:17 UTC (9:17 in Chile), with the
`FIREBASE_ADMIN_JSON` secret: `node tools/agents/popularity.mjs update` counts the games finished in the
last four weeks and rewrites `POPULARIDAD` and `POPULARIDAD_FECHA` in `games.js`. If the order changed, the
workflow opens a PR with a changelog entry, runs `tests.yml` and `e2e.yml` on its branch by hand (the
workflow token wakes nothing), waits for both, merges it and runs `publish.yml`. The label stays derived
(`populares()`: the first three that are not La Copa and not "New"), so the same merge gives it to the new
top three and takes it from the games that left. The processes round runs `update` by hand only when
`processes.mjs check` says the list is overdue, after looking at why the workflow failed.
**Why:** a cadence nobody has to remember; a PR keeps the change checked and visible in git, and the home
page still draws without reading the database (D-255).
**Alternatives discarded:** reading the order live from Firebase (D-255); storing the label per game
(it could disagree with the order); pushing straight to main (it would skip the required checks).
**Consequences:** `tests.yml` also accepts `workflow_dispatch`. The 🔴 gate's `lane` job runs only on `pull_request`, so it never sees this PR: by the owner's choice the workflow sets `owner-approval` green for its own commit, and only after checking that the commit holds nothing but the `POPULARIDAD` lines of `games.js` and its changelog entry; anything else fails the run and the PR stays open. The workflow can be run by hand from
Actions, with a dry run that only shows the count.
