## D-527 · A bug report starts with a failing test
**Date:** 2026-11-02 · **Status:** current · **Relation:** extends D-279, D-317, D-368 (how 🐞 feedback is resolved) · **Topics:** agents
**Context:** 🐞 reports of a bug (`feedback:problem`) were fixed by judgment: someone read the
report, changed code and checked by eye. "Fixed" meant "someone believed it", and the bug could
come back (#1090, part 5 of the automation plan).
**Decision:** before any fix, the processes agent writes the smallest test that reproduces the
report (an e2e in `tools/e2e/<game>/` or a unit `*.test.mjs` next to the game), named after the issue
(`#<n>` inside it, `issue-<n>` in the file name), and commits it first, so CI shows it red on the PR's
first commit and green at the end. `feedback.mjs repro <n> <test>` records it on the issue (the file
must exist and name the issue). `feedback.mjs reply` refuses a `feedback:problem` issue with no repro
unless it gets `--no-repro "<why>"` (not reproducible, device-specific…), and then the issue records
the reason. A fix PR touches only the game in the report. The example is #1103 (Shinobi's doubled
ninja), `public/cup/games/stick/issue-1103.test.mjs`.
**Why:** a test that failed and now passes proves the fix and keeps the bug from coming back; the
tool enforces it so it doesn't depend on remembering.
**Consequences:** a bug reply needs a repro or a written reason. The tests live with their game, so
`affected.mjs` keeps them in scope when that game changes.
