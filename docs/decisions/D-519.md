## D-519 · Merge lanes by blast radius
**Date:** 2026-11-01 · **Status:** current · **Relation:** amends D-216 and D-419 (auto-merge: not for a 🔴 PR), D-304 and D-413 (how much review: the lane, with the stage inside it) · **Topics:** publishing, agents
**Context:** how much review a PR got was spread over several decisions (D-413 lab fast lane, D-304 stage, D-355 splash pass, D-463 privacy page, D-216/D-419 auto-merge), each session re-derived it, and nothing stopped a risky PR (database rules, emails to players, workflows) from auto-merging (#1088).
**Decision:** a PR takes the lane of its riskiest file, read from `tools/agents/lanes.json` by `node tools/agents/lanes.mjs check [base]` (rule in `docs/LANES.md`):
- 🟢 contained and reversible (lab, docs, tests, changelog, marketing): no agents, auto-merge.
- 🟡 wide but reversible (the site, shared JS, tooling; any file no rule names): usability and documentation agents scaled by the stage (D-304, D-355), auto-merge.
- 🔴 hard to reverse (database rules, scripts that delete data or send email/notifications, the privacy page, workflows and release tooling, the gate itself): **never auto-merges**. The `lane` job in `tests.yml` labels it `needs-owner`, sets the `owner-approval` status red and opens a one-tap decision whose Yes is the new `approve-pr` action (approve.mjs), which turns that status green for that exact commit; a later push asks again.
The agents' confidence is never an input.
**Why:** the owner should be the gate only for what is expensive if wrong; everything else keeps its speed ("merge without asking" stays true for 🟢/🟡).
**Consequences:** `owner-approval` must be a required status on `main` (branch protection, set by the owner) for the gate to bind. MERGING.md and CLAUDE.md point to LANES.md instead of restating the cases.
