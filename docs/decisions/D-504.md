## D-504 · The owner is notified when a PR goes live, and every PR says where it is seen
**Date:** 2026-10-29 · **Status:** current · **Relation:** extends D-323 (publish.yml reports on the merged PR) and D-221 (the site's Web Push) · **Topics:** publishing, panel, pwa
**Context:** the owner kept looking for changes that had merged but were not live yet (publish.yml reruns the tests and the end-to-end run first), or looking in the wrong place: a splash campaign still off is seen in the panel's 📣 Campaigns, not on the home page. Sessions announced "done" at the merge. The owner decided (2026-10-28): a notification on their phone when a PR goes live, one tap to the exact place, short and precise.
**Decision:** the panel has **🔔 Notify me when something goes live**: it subscribes that device to the site's Web Push and keeps it in Firebase `ownerPush/<subId>` (only the owner reads and writes it). publish.yml's last job runs `tools/push/release.mjs`, which sends each device `✅ v<version> en vivo · PR #<n>`, one line saying what it launched and `👉 <where>`; if it did not publish, `❌ PR #<n> no se publicó`, the step that stopped it and `👉 Ver el error` (the run). The tap opens the PR's **`Ver en:`** line (a path of the site; a `Qué:` line, in Spanish, is the feature's line, else the PR title). Without it, it is worked out from the files: a splash campaign off → `/panel/#/campaigns/splash/<id>` (that campaign open and ringed), on → `/?splash=<id>`; a lab game → `/labs/<game>/`; a lab flag → `/labs/`; a game → its page; the panel → `/panel/`; anything else the site serves → `/`. A PR that changed nothing the site serves and has no `Ver en:` line sends nothing.
**Why:** the notification comes from the publish itself, so it arrives only when the change is really live and does not depend on a session remembering to report it; and the tap lands where the change is, not where the owner would have to search.
**Consequences:** every PR body has a `Ver en:` line (docs/MERGING.md); sessions report to the owner only once the change is live, with that link. The panel's routes take `#/campaigns/<tab>/<id>`. The service worker opens the repo's own GitHub run, the one link outside the site a notification may carry. `tools/push/release.test.mjs` checks the destinations and the message, `firebase/owner-push.test.mjs` the rules. On an iPhone the notifications reach only the site installed on the home screen (D-227).
