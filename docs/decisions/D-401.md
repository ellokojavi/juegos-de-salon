## D-401 · A decisions index left behind by other PRs no longer fails the next PR
**Date:** 2026-10-20 · **Status:** current · **Relation:** amends D-394 (a stale index failed the `tests` check) · **Topics:** agents, tests
**Context:** the index `docs/DECISIONS.md` is generated from the decision files (D-394), and every PR that
adds or amends a decision rebuilds it. Two such PRs merged one after the other (#587, then #584) each
rebuilt it without the other's change, so `main` was left with a stale index and the `tests` check
failed on every PR after them, for a file none of them touched. Leaving the count of decisions out
would not help: each row depends on its decision.
**Decision:** in the `tests` check, a stale index is rebuilt in the runner's copy before the tests and
noted as a warning, not a failure. The processes round sees it in `processes.mjs check` and rebuilds
it on `main` in its PR. Locally the test is still strict, and the merge driver still rebuilds the index
when pulling `main` (`.gitattributes`), so a session that writes a decision keeps rebuilding it.
**Why:** a race between two correct PRs is nobody's error, and blocking every later PR for it cost a
fix PR each time.
**Consequences:** `main`'s index may lag by a row until the next PR that touches decisions or the next
processes round. `.github/workflows/tests.yml` (the "Decisions index" step), `tools/agents/processes.mjs`
and `.claude/agents/processes.md` say so.
