## D-518 · CI failures are logged and promoted to mechanisms automatically
**Date:** 2026-11-01 · **Status:** current · **Relation:** extends D-273 (patterns and mechanisms of the processes agent) and D-441 (the `failure-log` branch is never "stranded") · **Topics:** agents, tests
**Context:** `processes.mjs pattern | mechanism` existed, but patterns were recorded by hand in the daily round, only when the agent remembered. Red `tests` and `end-to-end` runs and their fixes vanished into PR history, and the same mistake (a browser global imported into a Node test, the splash over a screenshot, a missing translation) was met again (#1087).
**Decision:** (1) `.github/workflows/failure-log.yml` runs on `workflow_run` of Tests and End to end on PRs: a red run adds one record per failing test (PR, branch, commit, check, test, first error lines, date, run) from `gh run view --log-failed`; a green run closes that PR's open records for that check, as **flaky** if it is the very commit that failed, otherwise **fixed** by that commit with its diff stat from GitHub's compare. (2) `tools/agents/failures.mjs` gives each record a deterministic signature: the test plus the error with paths, line numbers, hashes, times and durations stripped; no model. (3) A signature seen on two or more distinct PRs, not flaky, whose pattern has no mechanism, shows as ⚠️ ready in `processes.mjs check`; flaky signatures are listed apart (fix or quarantine the test). (4) `failures.mjs promote <signature> <key>` turns it into a `processes.mjs` pattern (the pattern keeps its `signatures`), and the round closes it with `processes.mjs mechanism`, preferring a test to a doc line. (5) Records older than 90 days whose pattern has a mechanism move to `archive.json`.
**Where the records live:** on a dedicated orphan branch `failure-log` of this repo (`failures.json`, `archive.json`), written by the workflow with its own `GITHUB_TOKEN`. Not `docs/failures.json` on `main`: `main` takes only PRs with green `tests` and `end-to-end` (D-216), so the bot would need a bypass or a PR per failure, and every record would be a commit on `main` that triggers tests, a publish and a version bump. Not Firebase `fallas/`: it is the players' database, its rules and archive jobs are about player data, CI would need the admin key as a secret, and the round would need that key to read them. The branch needs no secret, is readable from any clone (`git show origin/failure-log:failures.json`), keeps history, and holds only CI logs.
**Why:** every failure becomes a constraint without anyone noticing it twice; a deterministic signature keeps the grouping reproducible and testable; counting distinct PRs, not runs, keeps one stubborn PR from looking like a pattern; separating flaky runs keeps a retry from hiding as a "fix".
**Consequences:** `failures.mjs` and `failures.test.mjs`, `failure-log.yml` (in `tools/jobs/jobs.json`, whose test now accepts an event `trigger` instead of a cron for a GitHub job), the "CI failures" section of `processes.mjs check`, step 7 of `tools/jobs/prompts/processes-round.md`, `docs/AGENTS.md`, and `pending.mjs` skipping the `failure-log` branch.
