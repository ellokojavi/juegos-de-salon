## D-531 · A red PR is approved in its own description
**Date:** 2026-11-04 · **Status:** current · **Relation:** amends D-519 (where the owner's tick lives) · **Topics:** publishing, agents
**Context:** a 🔴 PR opened an `Owner approval: PR #n` issue, and every push closed it and opened another: PR #1169 left three issues (#1170, #1171, #1172) for one rename, and the owner had to look in two places.
**Decision:** the `lane` job writes the one-tap decision at the top of the PR's description, between `<!-- owner-approval:start -->` and `<!-- owner-approval:end -->`, and a push replaces that block in place. `approve.yml` also listens to `pull_request_target: edited`, so main's `approve.mjs` carries out the owner's tick; in a PR's description a box may only `approve-pr`/`merge` that same PR (or do nothing). Open approval issues of a PR are closed on its next push.
**Why:** one place to read and approve, no pile of stale issues; the gate itself (owner only, that exact commit, checks green before merge) is unchanged.
**Consequences:** sessions that rewrite a 🔴 PR's description keep the block. Old open approval issues still work until their PR's next push.
