## D-619 · The merge queue has a doctor: a free check every 5 minutes, a cloud agent that fixes it on its own, and fast PRs first
**Date:** 2026-11-24 · **Status:** current · **Relation:** extends D-586 and D-618; works like D-573 · **Topics:** agents
**Context:** On 2026-11-24 the `merge-queue` label was deleted and every queue step failed for over an hour, then a bug in the fix crashed it again. Nobody was told: the owner saw it only because the line was slow. In the same line, a two-minute tooling PR (the queue's own fix among them) waited behind half-hour game PRs. The owner wants the agents to ship every ready PR on their own; their approval only matters for a 🔴 PR.
**Decision:** (1) Every 5 minutes the heartbeat (`notifications.yml`, D-569) runs `merge-queue.mjs doctor --heal --alarm`, with no model: it remakes a deleted label, starts a queue step when a PR waits and none succeeded for 30 minutes, and keeps one issue, "Merge queue needs a look", with what is still wrong (two failed steps in a row, the in-flight PR's check running over 45 minutes, a PR with auto-merge on for over 4 hours and not merged; a 🔴 PR waiting for the owner is never stuck). It closes the issue when all is well. (2) Every hour the cloud scheduled task `queue-doctor` (`tools/jobs/prompts/queue-doctor.md`) runs `doctor`; on `NOTHING` it ends at once, otherwise it fixes what it finds on its own, ships the fix with auto-merge and never waits for the owner, except for a 🔴 PR. (3) The line goes by rank, then by age: a PR that changes the queue itself first, then one that changes nothing under `public/`, then the rest.
**Why:** Detection costs no model and runs where it is reliable (the heartbeat, not GitHub's late crons); the model works only when something is really wrong. A broken queue blocks every PR, so its fix goes first; a PR with no page changes runs a few end-to-end scripts in minutes, so it barely delays the next.
**Consequences:** A queue failure is caught within 5 minutes and handled within the hour without the owner. A long stream of tooling PRs could delay a game PR; each takes minutes, so the delay is small. The cloud task must be created from a cloud session (tools/jobs/README.md); if it is lost, the issue still says what is wrong.
