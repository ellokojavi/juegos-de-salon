## D-436 · Uno al día's ranking loads once and shows at once
**Date:** 2026-10-23 · **Status:** current · **Relation:** extends D-414 (the month's ranking on /today/) and D-409 (lab first) · **Topics:** random-and-daily, rankings
**Context:** the owner noticed the ranking on /today/ taking long to show. Firebase has the index (`.indexOn: k`), so the query is cheap; the time was on the client. Each load waited for the SDK, the connection, the table and only then for last month's champion, one after the other. The page draws itself up to three times (at once, after `sincronizar()`, when the player signs in), and each draw built a new `bloqueRanking` that went back to "Cargando…", read everything again and left one more sign-in listener behind. `leerMes()` also read the same month table the ranking read right after.
**Decision:** in the lab first (D-409), card `#seccion-uad-ranking-rapido`; **for everyone since 2026-10-23**, approved by the owner, the key check gone and the card in La Bodega, 🚀 Lanzado. /today/ builds the ranking once and keeps it across redraws (`bloqueRanking({ rapido: true })`), and a redraw calls `recargar()`, which keeps the list on screen until the new one arrives. With `rapido` the table and the champion are read together; `J.tabla(t, p, { reciente })` reuses a read of the same table started less than 5 s before (or still on its way), so the ranking takes the one `leerMes()` just made instead of asking again; the list each tab but Amigos showed last today is saved on the phone (`juegos-de-salon:rk-visto:<table>:<tab>`) and drawn while the first read loads; and the page, not the block, reloads it when the player signs in or out.
**Why:** all of it is client-side ordering and duplication, so it is fixed there, without touching the rules or the data. `leerMes()` reads fresh (it runs after the day's points are uploaded); only the ranking reuses, so a reused read is never older than the upload.
**Consequences:** The ranking under a game's result (`uno-al-dia-ui.js`) is unchanged.
