# Canons and standards of Juegos de Salón

Building rules for **every** game in the app, current and future.
Read them **before** building a new game and **before** changing an existing one.
Each canon has an ID (C-n) so it can be cited in code, commits and decisions.
Each canon's form (🤖 checked, 📈 ratcheted, 👁 judged) and what enforces it are in the generated index of [RULES.md](RULES.md) (D-541).

> If a canon gets in the way in a specific case, it is not ignored silently: the exception is
> documented in the game's spec and, if it suits everyone, this file is changed.

---

## C-1 · Identity and tone

- Informal Chilean Spanish by default; English and Portuguese are optional and chosen by hand (C-3, D-514). Informal "tú", light humor, no strong swearing.
- **The audience is everyone, not only Chile** (D-324). The app was first made for Chilean tables, and the Chilean Spanish voice stays as its flavor, but no text, document or decision presents it as being for Chileans only. Content only one country knows is tagged with its country and chosen by audience (🌎 Global, 🇨🇱 Chile, 🇧🇷 Brasil; D-187).
- **Concise instructions** (U-8, U-18, D-184): the goal first and with a verb, at most 3 points, nothing the example drawing already shows, and the scoring in one sentence. A cap in `public/cup/games/juegos.test.mjs` stops what goes over. Concise is not a telegram: full sentences (U-1).
- Palette and fonts shared from `public/assets/css/base.css`: dark background with gradients, neon accents (pink, yellow, cyan, lime), **Bangers** for titles and **Nunito** for body text. The fonts are served from `public/assets/fonts/` (never from Google Fonts), with their OFL license, and every page that links `base.css` preloads `nunito-latin.woff2` and `bangers-latin.woff2` (the title font, so titles do not flash in the fallback) right before it (#851, `public/assets/css/fonts-preload.test.mjs`).
- **Figures the player reads or compares** (keypads, attempts, secret numbers) use `var(--font-num)` (Nunito 900) with `tabular-nums`, never Bangers: there the 1 and the 7 are almost the same stroke and players get them wrong (D-30). Bangers stays for titles, names, words and room codes (letters, no I or O).
- No per-game "brand" styles: a game may have thematic colors (the sea in Batalla Naval), but buttons, panels, chips and titles come from the shared classes.
- **The design system** (D-533, [DESIGN.md](DESIGN.md)): every distance, corner, shadow and text size a game writes comes from the tokens in `base.css` (`--s-*`, `--r-*`, `--edge-*`, `--fs-*`), and a component that exists there is used, not copied. Thematic colours are declared once at the top of the game's stylesheet and listed in DESIGN.md's escapes. The usability agent owns the system; its lint (phase 2 of #1188) measures it.
- Each game has its own emoji that identifies it in the menu, the tab and the top bar.
- Closing moments with celebration: confetti and sound on winning or finishing a game.

## C-2 · Structure of a game

One folder per game inside `public/` (the site root: folder = URL), named in English,
lowercase and hyphenated (`public/hangman/` → `/hangman/`, D-192), always with these files:

```
public/<carpeta>/
  index.html      Screens as <section class="screen">, top bar, #handoff and #cover containers
  style.css       Only what is specific to the game: the shell (screens, cover, modes, fields, rows, room, result) lives once in base.css (DESIGN.md §2, D-533)
  rules.js        GAME_ID, DEFAULT_CONFIG and LOCALES = { es, en, pt, de }. Data, no logic or DOM
  engine.js       Pure rules, no DOM or global state. Testable with node
  engine.test.mjs Engine tests (node public/<carpeta>/engine.test.mjs)
  game.js         State machine and render. The only thing that touches the DOM
  game.json       Its manifest: what the catalog, the conformance suite and the boundary read (#1249)
```

- **The id is not the folder** (D-192): the `id` is data —rooms, the panel and
  `localStorage` keep it— and never changes; the folder is the URL and goes in `path`. A new game may use
  the same English name for both. If a folder is renamed, the old path stays as a
  bridge page (generated by `node tools/release/og.mjs cards`).
- The games built for La Copa (`SUELTOS`, a build, not a kind of game: C-21) follow the same idea in `public/cup/games/<carpeta>/`: `engine.js`
  (pure rules), `ui.js` (screen) and their own data; what they all share stays in `games/`.
  A game enters the Cup pool (`POZO`) with `copa: { pozo }` in its `games.js` entry, plus its loader in
  `cup/games/index.js`; `cup/engine.js` derives the pool and `manifest.test.mjs` checks both (#855).
  A standalone one still in the lab (`labs: true` in `SUELTOS`) has its page at
  `/labs/<slug>/`, and `/<slug>/` is a bridge page until it comes out (D-267).
  Every `/labs/` page loads the gate (`labs-puerta.js`) first and carries
  `<meta name="robots" content="noindex, nofollow">`, and its bridges carry the `noindex` too
  (`og.mjs` adds it to the ones it generates; D-281). In `/labs/`, a project goes in **Proyectos
  activos** while it is being tried and in **La Bodega** if it did not work out, folded to its title (D-280), or once
  what it tried reached everyone (D-372): whatever is implemented for everyone moves to La Bodega in
  the same PR, folded, a game to 🎲 Juegos guardados and an improvement to ✨ Mejoras lanzadas
  (D-479, `public/labs/bodega.test.mjs`). An improvement behind a runtime flag does not wait for that
  PR: when its flag goes to *all*, `/labs/` moves its card into ✨ Mejoras lanzadas on its own each
  time it opens (`public/labs/launched.js`, D-534), keeping its switch (D-510); the cleanup PR that
  removes the gate moves its HTML for good. The owner sends a feature live from its own card with **🚀 Publicar para todos**,
  which a headless session on the Mac mini turns into a PR with auto-merge (D-480).
- The game describes itself in its `game.json` (validated by `game-manifest.js`; `node tools/generators/new-game.mjs <id>` writes it with the rest of a lab game) and `games.js` imports it through `node tools/generators/manifests.mjs`. The catalog entry carries `id`, `emoji`, `name` and `tagline` per language, `players`, `duration`, `path` and `available`. With a room, also `jugadas`: the message types a person makes, which is what the panel counts as plays (D-138).
- The `<head>` of every app page carries the manifest, the icon and the iPhone name
  (`apple-touch-icon` and `apple-mobile-web-app-title`), the script that picks the language's manifest
  right after the `<link rel="manifest">`, the watchdog (`vigia.js`) before the stylesheets
  (C-7, D-251), and, after the stylesheets, the
  service worker registration (`import '<…>assets/js/instalable.js'`, which also sets the manifest and
  the chosen language's name, and brings `llegada.js`, which replays the Random game dice on top until
  the game is drawn: a `.screen.active` that is not `#screen-espera`, D-237; only on the
  game the dice opened, D-375): so the app
  can be installed from any game, with its name.
  They are copied from another game; `public/assets/js/instalable.test.mjs` requires them (D-221, D-222).
- Pages in git carry no import map: `set-version.py` writes it only in the copy that gets published,
  walking every module of the site, so a new game's modules get in on their own (C-11, D-192, D-205).
- Always reuse the shared modules before writing a new one:
  `public/assets/js/ui.js` (DOM, confetti, vibration, wake lock), `i18n.js`, `sound.js`, `session.js`, `handoff.js`, `transport/`.
  Same with the styles in `base.css`: a sheet that slides up from the bottom with steps or settings is the
  `.hoja` (with `.hoja-capa`, `.hoja-paso`…), the one used by La Copa's notices and the home page bubble (D-232).

## C-3 · Languages

- **Spanish is the default language.** Whoever opens juegosdesalon.cl without having chosen anything sees the app in Spanish, whatever their browser's language. English and Portuguese are optional: they only turn on when the person taps the toggle, and the choice is saved on the device (D-47). German left (D-514): whoever had it saved, or arrives with `?lang=de` or through `/de/`, gets English (`RETIRADOS` in `i18n.js`).
- **First visit in the browser's language (D-536, behind the flag `browser-lang` until the owner publishes it):** on a device where no language was ever chosen, the first page saves the first of `navigator.languages` the app speaks (or Spanish) as the choice, once, and reloads in it; from then on the saved choice and the toggle rule, and `?lang=` in a link still wins. Only `idiomaInicial()` in `i18n.js` reads it to decide.
- **The language can also come in the link:** `?lang=pt` on any page, or the `/pt/` and `/en/` doors. It is applied, saved, and the parameter is removed from the address bar. It is not detection: someone chose it, for themselves or for whoever receives the link. A room invitation carries it via `withLang()` (D-74).
- **The game's name is translated too (D-549):** a name the same as the Spanish one in another language needs a reason a player would accept (a proper name, a word already the same), listed in `SAME_NAME` in `game-names.test.mjs`; the test also checks La Copa's `texts.js` names match `games.js`. Moving a game to production includes reviewing its name in every language.
- Every visible text lives in `LOCALES.es`, `LOCALES.en` and `LOCALES.pt` in `rules.js`. No string literals in `game.js`.
- Fixed HTML texts are marked with `data-i18n="clave"` (or `data-i18n-html`) and applied with `applyStatic(T)`.
- The language is read with `getLang()` and the `langToggle()` toggle goes in each game's intro, with `coverLangToggle()`: behind the flag `compact-lang` it becomes one flag button in the top bar instead (D-537).
- **There is a single language selector, `langToggle()`, and it looks the same across the app** (D-231).
  No screen builds its own. Its standard:
  - A glass pill (`--glass`) with one button per language in `LANGS`, in `LANGS` order.
  - **Each button carries only its flag** (🇪🇸, 🇬🇧, 🇧🇷), without the ES/EN/PT code (D-524),
    at least 44 × 44 px (C-8), so the toggle stays narrow on any screen.
    The flag identifies the language, not the player's country: Spanish goes with 🇪🇸 (D-244). They come from `BANDERAS` in `i18n.js`, as emoji, never
    as SVG: on Windows it shows as two letters, and that is accepted (D-231).
  - The chosen one sits on yellow (`--yellow`) and slightly larger; the others on a transparent background.
  - Each button is at least 44 px tall (C-8) and names its language in that language for whoever
    does not see the flag (`NOMBRES_IDIOMA`, as `aria-label` and `title`): with no code beside it, that name is what
    screen readers and a hover give.
  - A new language brings its flag and its name: the parity test requires it.
- Translations are adapted, not copied: jokes and local references are replaced with equivalents. Portuguese is Brazilian, informal ("você", "celular", "rolê"), and game names are translated (Quarto Rei, Toque e Fama, Batalha Naval, Linha do Tempo) as in English (D-48).
- **In La Copa, what is personal goes in your language and what is the group's in the cup's** (D-170): the screen
  follows the viewer's toggle, but the words of Agentes, Conexiones and Palabra, the messages shared
  with the group and their link go in the language chosen when the cup was created. Word content
  is specific to each language, not a translation.
- **All dictionaries (`IDIOMAS`, the lab's too) have exactly the same keys**, lists the same length and templates the same `{llaves}`: a text missing in one language shows as `undefined` on screen, and `errText` (C-14) looks up the same key in any language. Checked by `node public/assets/js/i18n.test.mjs` (menu, phrases, decks and every game). Línea de Tiempo's decks carry `es`, `en`, `pt` and `de` on every card, and the engine test requires it too.
- Templates use `{llaves}` and a `fmt()` function; sentences are never built by concatenating loose words.
- **A new language comes in through the lab** (D-191): with all its texts (parity walks
  `IDIOMAS`), but in `EN_LABS`, which offers it only on the device that came in through
  `/labs/<idioma>/`. It leaves the lab once its speakers have reviewed it. Today there is
  none: German went through there, came out (D-197) and later left the app (D-514).

## C-4 · Sound and vibration

- Effects synthesized with Web Audio in `public/assets/js/sound.js`. No audio files.
- A 🔊/🔇 button in each game's top bar. The preference is saved and applies across the app.
- Audio is unlocked on the first tap (`initSound()`), an iOS requirement.
- There is sound on: button tap, the game's main action, result (good and bad), turn change, end.
- `vibrate()` accompanies important moments, never alone as the only cue.

## C-5 · Game modes

On every landing the modes (or the start button) come right after the cover, the title and the language toggle, and the rules and steps go below them (U-39, D-344).

A two-player game offers all three modes, in this order in the intro:

1. **📱 Un celular** (pass and play). It is the base mode and the fallback when the network fails.
2. **📡 Dos celulares** (a room with a 4-letter code and QR).
3. **One player**: **🤖 Contra el celular** when the game has hidden information that makes an AI meaningful (Batalla Naval, Dudo), or **🧍 Jugar solo** with score and record when a machine rival adds nothing (Línea de Tiempo, see D-27; Toque y Fama, see D-129). The menu card says "1–N jugadores".

A group game (more than two) chooses whether it is offered on one phone, on several, or both; what it
does not offer is not shown (D-213). "Próximamente", disabled and visible, is only for a
mode the game plans to have.

## C-6 · Game memory (required in every mode)

**Every game in progress can be resumed.** This applies to one phone, against the phone and two phones.

- It is saved with `createSessionStore(GAME_ID)` from `public/assets/js/session.js`, under `juegos-de-salon:<id>:session`, expiring after 12 hours.
- It is saved after every action that changes the state, not only at the end of a turn. It includes half-done work (a half-placed fleet, the player's notes).
- The intro shows a "⏯ Hay una partida a medias" panel with **Continuar** and **Borrar** while an unfinished game exists.
- When the game ends it is marked `done: true` and the panel stops being offered.
- Starting a new game deletes the saved one.
- In games with a message reducer the message list is saved and resumed by replaying it (`createLocalTransport({ seed })`); private data (secret number, fleet) goes in `private`, never travels over the network.
- When resuming in one-phone mode, the pass screen or the covered screen is shown again: nobody knows who has the phone.
- Writing to `localStorage` can fail (private mode, quota). Always in `try/catch`: if it fails, the game keeps working without memory.
- The player's name is remembered between games with `createNameStore(GAME_ID)`. A group game on one phone also remembers the whole table with its `list()`/`setList()` (`juegos-de-salon:<id>:names`); an old key of that list goes in `legacyKeys` and moves over on its own the first time.

## C-7 · Transport and multiplayer

- A game's state is derived from a **list of messages** (`view()`), never from loose turn variables. That way reconnecting is "reading the messages again".
- Messages are processed in series; duplicates and out-of-turn ones are dropped in the reducer.
- **What is dealt comes from the seed:** cards, words and everything dealable are derived from the
  shared seed that goes in the message list, so each phone reaches the same deal without
  sending it. The exception is what is hidden and nobody must be able to compute from the code, which is public:
  Dudo's dice go committed with hash and salt (D-70) and Julepe's hands in sealed envelopes
  (D-81). See C-10. And what is thrown in plain sight is not dealt: Generala's dice are
  thrown by the phone of whoever is playing and travel in the clear, because with the seed the
  next throws could be computed (D-246).
- Every mode uses the same logic: the transport changes, not the game.
  `public/assets/js/transport/local.js` (same device, also for the AI) and `firebase.js` (remote room).
- Creating and joining an online room goes through `public/assets/js/room-flow.js` (`roomFlow({ game, maxPlayers, defaultConfig, start })`, #860): the game keeps only its own `startOnline`.
- The room's own messages go through `public/assets/js/room-state.js` (D-539): `apply()` calls `roomMessage(M, msg, { minPlayers, onStart })` first and handles only the game's moves after it (seen ids dropped, the host's single `start`, the first rematch offer of each seat). A game with something hidden works out its phase with `phaseOf()` in `hidden-match.js` and accepts the commit and the reveal in any phase.
- Transport interface: `create`, `join`, `send`, `onMessage`, `onPresence`, `leave`, `dispose`.
- **Reserved transport fields:** `from`, `at` (timestamp) and `id`. A game that needs to send a position or an amount uses another name, or the transport will overwrite it without warning.
- **Firebase does not store an empty list:** the field simply is not kept. A list that can be empty travels as text (`"1,4,8"`, or `""`) and the engine reads it accepting the string, the local transport's raw list and the missing field (D-60).
- Rooms: a 4-letter uppercase code with no I or O, a QR with `?room=CÓDIGO`, a `game` field to separate games, expiry after half an hour with no plays and 6 hours in total (D-89). Roles A to F (up to six players).
- **The connection is awaited before touching the room.** Creating or joining waits for `.info/connected` (8 s) and runs with a cap (12 s), and the per-phone room cap is checked before the network (`errors.js`, `ratelimit.js`). Without that, losing signal looks like a button stuck forever.
- **A phone cannot open rooms nonstop:** 20 per hour and 80 per day (D-41). The cap sits above the most intense legitimate use, not the average, because a rematch opens a new room. If `localStorage` fails, creating is allowed: blocking a legitimate player is worse than letting an abuser through.
- **Every game leaves a usage signal for the owner's panel** (`public/assets/js/transport/stats.js`, D-44). The transport records rooms on its own; offline modes call `trackStart({ game, mode, players })` on starting (not on resuming) and `trackFinish({ ganador, empate, detalle })` on finishing. It is a REST `fetch`, no SDK, best effort: never awaited or shown. An offline mode sends who is playing —the names the game already has (`nombres` in `trackStart`) or, if there are none, the last one the person typed in the app (`nombreDelCelular`)— and how it ended, once (D-210), plus the language chosen in the app (D-211). A secret, the chat or an IP never leaves. Whoever **signs in on purpose** with their name and PIN for the rankings (D-212) also sends their best score and their games to their player; without signing in, none of that. From a **room** the phone's country and who won are also kept, which is what the panel shows as a log (D-79). An offline game shows live in the panel because `trackStart` starts a heartbeat for it (D-140): the game does not have to do anything else.
- **Every page that loads modules carries the watchdog** (`<script src="…/assets/js/vigia.js"></script>`
  in the `<head>`, before the stylesheets; not in the panel or in bridges, D-251): it records what
  fails on loading or playing for the panel's Salud (health) section. "Started" is reported by `trackVisit`, so
  the page calls it on load, as it already did. Checked by `public/assets/js/vigia.test.mjs`.
- **Room writes nobody waits for are handled in the transport** (`public/assets/js/transport/best-effort.js`,
  D-320). The games fire `send()` and move on, and nobody awaits the presence writes either, so a
  rejection there would reach the vigía as an unhandled one. `firebase.js` passes the `push` of
  `send()` through `message()` and the presence writes and the background room note through
  `quiet()`. A denied message that is already on the server is a resend after a reconnect (the SDK
  sends again every write whose ack was lost, and a message can only be written once), so it is not
  reported; any other failed message is raised again so the vigía still counts it, and a failed
  presence write or room note only goes to `console.warn`. `send()` still returns the same promise.
  `best-effort.test.mjs` fails on any Firebase call in `firebase.js` that nobody awaits, returns or catches.
- **Leaving on purpose closes the room.** `leave()` releases the listeners and leaves the room waiting; `dispose()` is the goodbye: it writes `left` on the role and deletes the room if nobody is left inside (`public/assets/js/transport/dispose.js`, D-50). It is called by the lobby's cancel or leave-room button, the change-mode button at the end and the move to the rematch room. **Closing the tab or losing signal is not leaving:** that only turns off `online`, because that game can be resumed (C-6), so none of this hangs from `pagehide`. It never throws, has a short cap and, if it fails, the room stays marked and the trash bin deletes it.
- **Expired rooms delete themselves.** On creating or joining a room, the phone notes it in the trash bin (`cleanup/days/<día>`, `public/assets/js/transport/cleanup.js`, D-39). A new room is noted in the same write that creates it, so a room that exists is always in a bucket (D-321). Phones do not sweep: the nightly `room-sweep` job deletes the expired rooms of every closed bucket and the unnoted ones (`tools/firebase/room-sweep.mjs`, D-499). None of this is shown to the player or can overturn a game.
- Taking a seat is a race: two phones can join at the same instant. A seat is taken with a Firebase transaction that writes the phone's `uid` only if no other phone holds that seat, so exactly one phone gets it and the other moves on to the next free seat, or hears the room is full (`public/assets/js/transport/seat.js`, #850). The first free seat that was read is never assumed to still be free.
- With more than two players, one is the host (role A) and starts the game when everyone is in.
- Whoever opens a room link (`?room=CÓDIGO`) lands on a screen that **only** lets them join that room: its own invitation title, no button to create another, the code fixed and read-only, and the game settings are not shown because the host sets them. Offering both confuses whoever was invited.
- The room link is shared with the system's native dialog (`botonInvitar` in `public/assets/js/compartir.js`); copying to the clipboard is only the fallback when the browser has no such dialog. The phone's dialog already includes copy, so nothing is lost.
- **Everything shared** goes through `public/assets/js/compartir.js` and follows its standard (D-165, U-30, U-33): a header `{emoji} *{título}* · {contexto}`, one idea per line and the link alone at the end; if an image goes along, it carries the same header above and the same link below (`lamina`, `laminaResultado`), and is sent together with its text. Invitations go as text only; the app, from the home page, with its language's social card as image (`compartirApp`, D-226) and a text that names everything main, one line each (`LO_PRINCIPAL`, D-271, U-35). A new game does not build its own message or its own button.
- It is shown when the rival disconnects, and it resumes on its own when they come back.
- The rematch creates a new room and moves both players; whoever lost starts.

## C-8 · Touch interface

- Touch targets at least 44 px; small controls carry an invisible enlarged touch area.
- `.app` measures `calc(100svh - muescas)`, the screen's small height, not `100dvh`: what sits at the bottom must also show when the browser shows all its interface. Checked with `node tools/e2e/look.mjs <juego> <pantalla> --notches` (D-77).
- Irreversible actions are confirmed: select and then confirm (for example pick a cell and tap "¡Fuego!").
- **Nothing is preselected** in a move that gets confirmed. The app does not choose for the player: with no explicit selection, the confirm button is disabled. In a scrolling list a tap can turn into scroll and never land; if something was preselected, the player ends up confirming what they did not choose (D-38). A game setting may come with a default value, if it is visible and can be changed before starting (D-213). A **move** is what is chosen during the game and confirmed with a button (a cell, a card, a bet, an answer). A **setting** is what is chosen before the game starts and holds for all of it (players, deck, theme, number of rounds, the gender in Cuarto Rey, a cup's options on creating or joining it), even if it is chosen between one game and the next.
- The confirm button **says what it acts on** ("Colocar aquí · 🔍 Se funda Google"), not just the action.
- Nothing important below the fold on an 812 px phone: the end screen's buttons must show without scrolling.
- If a list can grow without limit, the confirm button floats (`position: sticky; bottom: 0`) with a gradient behind it, never at the end of the content.
- Long blocks (game review, rules) are collapsed by default.
- No horizontal scroll. Grids and tables adapt to the width.
- **Room between the board and its buttons** (D-309): the game board, and whatever sums up the game on the result, carries `data-tablero`; `base.css` gives it 28 px (`--aire-tablero`) to what is below, minus the container gap (`--gap-contenedor`) and the button bar's padding (`--aire-ya`, which the game declares). It is not separated with loose margins. Each script screenshot measures it and marks ✗ under 24 px; `look.mjs` reports it.
- A grid's labels (letters, numbers) go **inside** the same CSS grid, as one more row and column; never in a separate container aligned "by eye", because each browser stretches it differently (it happened in Safari with Batalla Naval).
- `prefers-reduced-motion` is respected.
- A tap outside a selected element deselects it.
- **Whose turn it is shows without reading** (D-92): with redundant cues —the color and shape of the status bar or the lit seat, what is tappable alive and the rest dimmed—, an out-of-turn tap that responds (C-8b) and, when the turn arrives, `SFX.turn()` with vibration.
- **Dragging is choosing, never confirming** (D-85). Wherever there is dragging, dropping leaves the move
  chosen and the irreversible action still hangs from the button that names it; the tap path
  stays intact, and the gesture comes from `public/assets/js/arrastre.js`, not an implementation of its own.
  The browser cannot take it over: `overscroll-behavior: none` on `<html>` and `<body>` (so
  pull-to-refresh does not reload the game) and `touch-action` on the whole drag zone, not
  only on each piece (D-86). A new gesture is tested on a real phone (D-67).
  The phone's own back gestures (iOS's edge swipe, Android's Back) cannot be blocked: since D-432
  (for everyone since 2026-10-23), while a game is on, `public/assets/js/back-guard.js` catches them and asks
  «¿Salir de la partida?»; the header's «‹ Menú» (`a.back`) asks the same, and Salir follows it.
  `trackStart` arms it and `trackFinish` / `trackEnd` disarm it, so a game that reports its start and
  end gets it without code of its own.
  What is dragged is drawn large and **above the finger**: if the text was small in the
  list, dragging it under the finger leaves it just as unreadable and covered too.
- What the player needs to remember (their secret number, their fleet) is shown on screen, covered if the phone changes hands.

## C-8b · Player errors

- An error is shown with an unmistakable cue (color, shake, its own sound) and stays on screen until the player taps; it never closes on its own and another player's move never overwrites it.
- That cue is **for whoever made the mistake**. The others get the same fact as news, in third person and without the red background: “¡Cata se equivocó!”, not “¡Te equivocaste!” (D-36).
- It comes with a short, concrete explanation of what was wrong, with the game's data (for example, between which milestones the card went and between which it was placed). **Exception, when the answer already shows** (D-277): in Línea de Tiempo, ⏳ Línea Relámpago and 📅 ¿En qué año? the card's year, large, already says what was wrong; instead of repeating it, the verdict tells the card's **fact**, something the player takes away, and tells it on a correct answer too (D-314). If the game runs against the clock, the clock pauses while it is read, with a cap. A card with no fact again says between which milestones it went.
- A correct answer or another player's move may close on its own after a couple of seconds (as long as reading its fact takes, with a draining bar, D-314), if no phone pass comes after it; a tap closes it sooner. If a pass comes, C-9 rules (D-213).
- The timer that closes a notice can only close that notice, not a newer one.
- **Exception, when erring is the normal move** (D-56): in El Ahorcado, a letter that is not in the word does not open a notice to close in the modes where the phone does not change hands; it is signaled through four channels (color, shake, sound and the drawing advancing) and the game goes on. The round's verdict does stay until the player taps.

## C-9 · Pass-the-phone transitions

- In one-phone mode, between turns there is always: **the result of what just happened** and, below it, **"Pásale el celular a X"** (pass the phone to X) with a button. The result is never skipped.
- `public/assets/js/handoff.js` (`showHandoff`, `passBlock`, `showCover`) is used, not an implementation of its own.
- When there is a pass button, only the button advances: an accidental tap cannot close the screen before it is read. The result stays until the button; nothing closes it with a timer (D-213).
- Secret information is covered with `showCover` before the next player looks.

## C-10 · Anti-cheat

When each device keeps a secret (a number, a fleet):

- On setting it, `sha256(secreto + sal privada)` (secret + private salt) is published; the salt is revealed only at the end.
- At the end the secrets are revealed and each device verifies the hash **and** recomputes every answer the rival gave.
- The result is shown to the player: "verificado ✅" or "⚠️ no coincide".
- The secret never travels over the network during the game.
- **What is hidden but must travel** does not come from the seed (C-7): dice are thrown on each phone and `sha256(dados + sal)` is published, verified on uncovering (D-70); a deal is sealed per player, with each one's public key (`public/assets/js/sobre.js`), and when the hand closes each one uncovers theirs to verify it against what was played (D-81).

## C-11 · Publishing and versioning

- A release's version is the first entry of `CHANGELOG.md` (`## X.Y.Z — fecha`) bumped once for each `changelog/` entry not yet gathered, in the order they reached main (`tools/release/changelog.mjs`, D-300). Each PR leaves its own without a number in `changelog/<rama>.md`. Pages in git do not carry it (D-205).
- On publishing, `publish.yml` runs `set-version.py --site _site`: stamps each file with `?h=<8 hex of the sha256 of its content>` (D-467) in the import maps, the stylesheets, the classic scripts (the watchdog, D-251), the `<link rel="modulepreload">` hrefs (home page) and the card images, writes `<meta name="release" content="X.Y.Z-<commit>">` and the version in the menu footer, only in the copy that gets uploaded. Right after, `tools/release/precache.mjs --site _site` writes `precache.json`, the list offline mode stores (D-538). A publish that changes one file invalidates only that file (and the pages' HTML), and two open PRs do not collide.
- The README (C-13) and the cards (D-181) falling behind is stopped by each PR's `tests` check, and checked again before publishing.
- New modules get in on their own: the script walks the site's `**/*.js` and stamps every page that loads modules (D-192).
- Only `public/` is published, with `.github/workflows/publish.yml`, on each merge to main and only if the tests and the end-to-end pass (D-192, D-302).
- The menu draws the game list **before** any decoration, and decorations go in `try/catch`: a broken decoration cannot leave the app empty.
- Each published change goes into `changelog/` without a number, and the processes agent gathers it into `CHANGELOG.md` with its version (D-300).
- The published site is checked to serve the new version before calling it ready: the last step of `publish.yml` does it (D-205).
- The PR's session learns of the merge without the owner (D-323): with auto-merge on, the last step of the required `end-to-end` check comments on the still-open PR that it merges now (`tools/release/merge-report.mjs --ready`), without holding the check; the session learns of the merge with `tools/agents/wait-pr.mjs`, which it runs in the background after turning on auto-merge (D-400). After publishing, the `report` job of `publish.yml` comments on the merged PR "✅ Merged and published" with the version, or "❌ Merged, but not published" with the step that stopped it: a record, not a wake-up.

- Each game's engine has tests that run with node, without a browser. GitHub runs them all on each PR and each merge to main (D-143): a PR with ❌ is not merged. `main` requires `tests` and `end-to-end` (the summary of the scripts in Chrome), and a ready PR carries auto-merge: GitHub merges it on its own when both pass (D-216). - **Every screen is tested in every offered language** (D-199): each game's `languages.mjs`

## C-14 · Robustness

- No npm dependencies and no build step: the published repo opens and works.
- External libraries (QR) are loaded on demand and their failure does not break the screen. The room QR is drawn by the shared module `public/assets/js/qr.js` (`renderQr`), which loads a copy of the library served by the site itself (`public/assets/js/vendor/qrcode.js`, qrcode-generator 1.4.4, unchanged), never from a CDN; a game does not carry its own copy of that code.
- Each game exposes a read-only `window.__…` hook for automated tests, named in the game's spec (D-213).
- The screen does not turn off while playing (`keepAwake()`).
- An animation that runs on its own (a cover's demo) draws through `onScreen` (`public/assets/js/on-screen.js`), so it stops asking for frames while scrolled off screen; a loop bounded in time or tied to a turn does not need it (#883).
- Foreseeable errors are shown to the player in their language, with a clear way out; never a blank screen.
- **The message does not invent the cause.** If the browser cannot tell two causes apart (losing signal and hitting the connection cap look the same), the text names both instead of picking one. False precision is worse than honest vagueness (D-40).
- Transport errors are translated with `errText`/`failWith` from `public/assets/js/transport/errors.js`, never with a map of their own in each game.
- Creating or joining a room goes through `tryRoom` (same module): the button says it is waiting, and a room that can't be reached offers one-phone mode under the message (U-37, D-319).
- The rematch button goes through `tryRematch` (same module): if the new room can't be opened or joined, the room text shows under the button and the button comes back; it never fails silently or leaves an unhandled rejection (D-322).
- **A retry never jams** (U-22, D-123): if a write that happens only once collides on retrying, first check whether the earlier one arrived (even if the phone showed an error); if it did, carry on as if it had succeeded.
- **Only the unexpected goes to the console.** A foreseen error already shown to the player is not logged: if the console fills with normal failures, "console without errors" stops working as a criterion (C-12).

## C-15 · Room chat

Only in **several-phone** modes: on one phone people are looking at the same screen and talking out loud, and solo there is nobody to talk to.

- `public/assets/js/chat.js` (`createChat`) is used, not an implementation of its own. Texts come from the game's `LOCALES` (C-3).
- A text field in a fixed layer (chat, the 💬 feedback form) keeps clear of the iOS keyboard with `public/assets/js/keyboard.js` (`followKeyboard`, which sets `--kb` from `visualViewport`), not its own listener. The feedback form uses it behind `flag('keyboard-lift')` (#883); `chat.js` still has its own copy of the same logic until it is moved over.
- It lives in its own container (`<div id="chat">`), a sibling of `#handoff` and **outside** the `.screen`s: the game's re-renders cannot erase what the player is typing.
- Messages travel through the same transport as moves (`{ t: 'chat', text }`), but **are not part of the state**: the reducer draws them and does not keep them. A chat message does not redraw the game.
- The chat **dies with the room**, not with the game: it stays alive on the win or loss screen, which is where the conversation wraps up on its own (D-35). It is not saved in the game memory (C-6), and the rematch creates a new room and therefore a blank chat. On reconnecting it is recovered from the room, without sound or unread badge.
- It does not appear over verdict screens: the chat goes under `#handoff` and closes on its own when the player's turn comes (unless they are typing).
- The bubble lives in a strip of its own at the bottom of the screen: with the chat on, one shared rule in `base.css` (`body.chat-on .screen.active`) makes every room screen end above it, so it never covers a button or the board (C-8). A game does not add its own padding for the bubble; a sticky bar stops above it. Check a screen with `node tools/e2e/look.mjs <game> <shot> --chat`.
- A floating bubble with an unread badge; a discreet sound and short vibration on receiving, subject to the mute button (C-4).
- A new message peeks for a few seconds beside the bubble, with the sender's name: the badge says *how many*, the label says *what*. It can be tapped to open the chat and disappears on its own.
- Limits: 120 characters per message, one message every 1.2 s per phone and the last 60 on screen. The Firebase rules validate the text length.
- The room can be read just by knowing the code: the chat is not private and is not used for anything sensitive.

## C-16 · The panel learns on its own

The owner's panel (`/panel/`) keeps no list of its own of games, modes or languages:
it reads the same lists the app uses and draws the signals that reach it. **A new game, mode,
language or environment has to show up there without anyone remembering to go edit it**,
because the day a game is added nobody remembers the panel, and a missing figure does not look
like an error: it reads as nobody having played.

- **One list per axis, and only one.** Games and modes live in `public/assets/js/games.js`
  (`GAMES`, `MODES`, and from there come `gameLabel`, `modeIcon`, `ROOM_MODE`, `LOCAL_MODES` and
  `MAX_PLAYERS`); environments, in `public/assets/js/transport/stats.js` (`ENVS`); languages, in
  `public/assets/js/i18n.js` (`LANGS`). The panel imports them. It does not copy them **anywhere**: not in
  the JavaScript, not in the HTML options, not in a per-mode CSS rule.
- **The unknown is shown, not dropped.** A signal from a game, mode or language
  the panel does not know is drawn anyway, with its raw key as its name. It always happens: the published app
  starts sending the new thing before anyone looks at the panel, and what belongs to a game that already
  left the menu stays stored. Dropping it silently is lying in the total.
- **The shape is validated, not the list.** The rules in `firebase/database.rules.json` accept a
  mode by its shape (`^[a-z][a-z-]{0,15}$`, the same as `MODE_KEY`) and not by enumeration, as
  they already did with the game id. A list in the rules is worse than a list in the code:
  it rejects the signal on the server, the game never notices and the data never exists again.
- **No hand-written cap.** How many players fit comes from `MAX_PLAYERS`, derived from the
  largest game in the registry. A game of eight raises the cap on its own (and forces growing the
  room roles `A`–`F` and the `$p` pattern in the rules, which is a separate change).
- **Color and icon are handed out, not assigned one by one.** Bar colors are
  taken in palette order and the icon comes from the registry: a new mode comes in with its color and
  with `·` until someone picks it an emoji, never gray or invisible.
- **A test watches it, not memory:** `node public/panel/adapta.test.mjs` invents a game, a mode and
  a larger game, and requires them to reach the bar; it also fails if the panel or the
  rules name a game or a mode again. To look at it: `node tools/e2e/look.mjs panel data`,
  which seeds the panel with a game and a mode that do not exist.
- **What does have to be touched by hand:** a new signal **category** (something that is not game,
  mode, players, time zone, language or hour) needs its line in the rules, its section in
  the panel and publishing the rules in the console (see [PANEL.md](PANEL.md)).

  asks it inside (D-149). With a filter on, the line below says "Se ven n de m" and
  offers "Ver todos" (D-149; #71, resolved in [USABILIDAD.md](USABILIDAD.md)).
- **⭐ Favoritos is one more filter**, exclusive with the types, and appears only with some favorite
  marked. Favorites belong to that browser (`localStorage`, by game id), with no account
  (`favoritos.js`, D-238). La Copa cannot be marked, nor a game that is not available. Unmarking
  one while in ⭐ Favoritos does not remove it from view (it can be marked again), unless none
  is left: then all are shown.
- **The filter goes in the URL, in English** (`?type=logic`, `?type=favorites`): coming back from a game
  leaves it as it was and a filtered link can be shared. An old link (`?tipo=`) is rewritten
  and one that does not apply (`?jugadores=`, or `?type=favorites` without favorites) shows all without warning
  (D-149, D-214, D-238).
- **The filters stick to the top** when scrolling down the list, and tapping one while stuck
  goes to the first filtered card (D-196). Stuck, their background rises to cover the notch
  strip: cards are not seen passing behind the clock (U-12). They keep floating after that tap even when the
  result is too short to scroll that far: an empty space under the list (`.filtros-relleno`) holds
  them, and shrinks as the player scrolls up, so they leave at the first pixel up; the jump is
  rounded up to a whole pixel (D-371).
- **The types go in a single row**, at any width from 320 px and in the three languages:
  with the row under 560 px the emoji moves above the name (five types did not fit at 900 px in es and pt), and under a 300 px box the chips tighten so as
  not to stick to the edge (D-144, D-149, U-11). What is added to the row gets in only if it fits,
  and that is measured on the page, not assumed: ⭐ Favoritos goes first, with its name or with the ⭐
  alone and less room between chips, and if it still does not fit (at 320 px, almost always) it goes on its own
  line above the types (D-238, D-241).
- **Nothing overflows the screen at 320 px**, not even where the browser cannot break a long
  word ("Galgenmännchen" in Chrome on Linux): the card column does not grow wider than the
  screen (`minmax(0, 1fr)`, D-238).
- **Nothing inside a card is tappable**: the card is one whole link. What is tapped
  without opening the game, like the ⭐, goes beside the link, on top of the card (`.game-slot`), with
  a 44 px touch area and without covering text (C-8, D-238).
- **The top bar** comes in two blocks: the language (C-3) on the left and, on the right, the
  actions: sound (C-4), 🏅 rankings (D-212, open to everyone since D-217; a medal and not a cup, so it is not confused with La Copa) and share. With
  6 px between buttons they fit on one line from 375 px; narrower (320 px), the actions
  drop to a second line and stay on the right (v0.128.1). In every language, share opens a sheet (the one from D-223 and D-232) with the vertical
  promo Shorts under two tabs, 🇪🇸 Español and 🇬🇧 English (Spanish opens on its own tab, the other
  languages on English), playing muted on their own (D-410), and two options: **Invitar a
  jugar** (invite to play), which shares the app with its social card in the language being viewed (`compartirApp`,
  D-226, U-33), and **Compartir el video** (share the video), the Short of the tab on show (`SHORTS` in `compartir-portada.js`,
  D-253, D-410). Its icon is the operating systems' share icon, an
  open box with an arrow pointing up, in SVG and not an emoji (D-242), with the box light blue,
  the arrow pink and the bottom shadow of the page's buttons (D-243).
  The bubble inviting to add the app to the home screen shows at the bottom, only on phones where it can be
  added (not on the computer or in the already-installed app), and the ✕ turns it off for good in that
  browser (D-232).
- **The footer's last line links the privacy page** (D-463): the version, "código en GitHub" and
  "Privacidad" (`COMMON.privacy`), which opens `/privacy/`. The same page is linked from the note
  under the email field of every feedback form. **The page describes the code:** a PR that stores
  something new about players, or keeps it for a different time, edits `public/privacy/texts.js`
  in the same PR, in the three languages (`texts.test.mjs` checks their shape).
- **The footer outside the home page:** game covers (the one-player games' too, on their own page, not in La Copa or Uno al día), La Copa's entrance,
  Rankings and Uno al día end with the same violet-sunset footer (`site-footer.js`, U-38); only Rankings
  and Uno al día carry the funny phrase. Never during a game or on a result screen. **Every game is a game** (the owner, 2026-10-27; C-21): no player text or doc calls one a "minigame"; only La Copa's Gran Final plays shortened versions.
- **It is tested whole in Chrome:** `tools/e2e/favorites.mjs` (filters, favorites and 320 px in the

## C-18 · URLs in English

Everything visible in an address is in English: folders (`/hangman/`, C-2, D-192),
parameter names (`?room=`, `?seed=`, `?test`) and their word values (`?type=logic`,
`&demo=podium`, `&notif=deadline`, `?practice=queens`), also in the panel's `#` (`#/cup/OFICI`).
The old names are still read as aliases: a link already circulating does not break (D-214, D-266).

- **It is read and written with `parametros.js`.** `param('room')` reads the new name or the old one and
  returns the value in English; `tiene('test')` does the same with a flag. A new parameter
  is added there, in English, and one that changes name leaves the old one in `ALIAS`, `BANDERAS` or
  `VALORES`. Nothing reads `location.search` by hand with a Spanish name.
- **What the app generates always uses the new name:** invitations, shared links, phone
  notifications (`tools/push/`), what it leaves in the address bar with `history.replaceState`. On opening a page,
  `trackVisit()` rewrites an old address in English (`normalizarUrl`).
- **The game in the URL goes by its folder name** (`slugDe` / `idDeSlug` in `games.js`): the id
  (`reinas`) does not change, because rooms, the panel and the phone keep it, but it is not seen.
- **A stored key does not change because of this:** the panel still counts `aviso/plazo` even though the URL
  says `notif=deadline` (`AVISO_CLAVE`).
- **What is not a word stays as it is:** codes (`?K7Q2X`, `?c=`), a cup's own link
  (`?pirata`, chosen by whoever creates it; the flags' words are reserved).
  Code variable names are no longer an exception: everything internal is English (D-316, which
  amends D-266 here), renamed in phases.
- **A test stops it:** `node public/assets/js/parametros.test.mjs` searches `public/` and
  `tools/push/` for a URL built with an old name.

## C-19 · The way out of a result screen

Every end screen (a game's result, a Cup day, the Cup's podium) offers the exits that are right at
that moment, and only those, in the same order everywhere (D-343):

| Context | Main action | Secondary | Exits |
|---|---|---|---|
| A Cup day | **Back to the board** | Share · next-day notice | none: the board is the Cup's home |
| The Cup's podium | **Share the summary** | My days, the table | **🏠 Back to the menu**, under the podium; "Leave this Cup" stays a quiet link |
| One a Day (any game) | **Share** | 🎲 Play another · Replay today's | **📅 Back to One a Day**; the menu is the header's ‹ (one way to it, not two) |
| A game played on its own | **Play again** / Rematch | Share · Change mode | Back to the menu (or to the lab) |

- **Blocks in this order:** the result (emoji, title, score, place) → the context (the One a Day
  card) → the actions → the exits → the long detail, folded or below (breakdown, words, fleets,
  history) → rankings → one feedback link, 🐞 or 💬, last (U-38).
- **The main action and the exits show without scrolling** at 390×812 and at 320 px, in the four
  languages (C-8): measured, not guessed (`getBoundingClientRect().bottom <= innerHeight`). What
  goes above them (the Sign in offer inside the One a Day card) is one line (`compacto`).
- **One primary (yellow) button per view**: the rest are cyan or ghost. A card that offers
  something extra under a result (the Cup's next-day notice) does not compete with it.
- **No exit twice:** where the header's ‹ already goes to the menu, the result does not add a
  second "back to the menu" next to another exit (One a Day).
- **The exits come from `public/assets/js/fin.js`** (`salidasFin(contexto)`): the same words and
  look in every game. A game does not build its own "back to the menu" (or "back to the lab",
  `salidasFin('lab')`) for these contexts; `fin.test.mjs` fails on a hand-built one (#1042).
- **The header's ‹ goes to the screen's logical parent and names it** (#1042): «‹ Menú» on a hub
  or a game played on its own, «‹ Laboratorio» in a game opened from the lab, «‹ Volver a la copa»
  on a Cup day (its cover, while playing it, its result) and a trial run goes back to its day's
  cover; a cup's board says «‹ La Copa» and goes to La Copa's home (`/cup/`, with «Tus copas»). Mid-game it asks first (D-432).
  A button that goes back one step inside a game (setup → intro) says «‹ Volver», never «Menú».
- **One a Day is one card in every game**: `tarjetaResultado` (`uno-al-dia-ui.js`) carries its
  actions and exits, and `ponerTarjeta` puts it right under the hero. In today mode the game adds
  no buttons of its own: no rematch (#226), no change mode, no second menu button.
- **Never offered at the wrong moment:** play again in a Cup day (it is played once, U-21), a
  link to La Copa from One a Day (a Cup is joined by invitation), the menu inside a running Cup
  (the header's ‹ already goes there).
- **What a result says, once (D-353).** A result screen is read in a glance, so each fact appears
  in one place only:
  - **The score, the time, the winner and the game's name** each appear once. The hero says them; a
    card or a sentence below does not repeat them ("Hoy: 80 puntos", "Tu tiempo fue 1:20",
    "Total: 80 puntos", the champion named again as an award). A share card that only restates the
    score (Desenredo's 🧶 🟩🟩) goes in the shared text, not on the screen.
  - **The subtitle adds, it does not copy:** what the detail below already shows (each fleet's
    shots and aim) is not said again under the title.
  - **The long detail is folded or after the exits:** the score breakdown (🧮, always folded),
    boards, words, history. It never pushes the main action down.
  - **Sign in is one line:** the same `bloqueJugador({ destacado, compacto })` card everywhere, also
    for "¿Quieres que esta partida cuente?" (D-274); tapping it opens the form with the name in.
  - **Secondary offers fold:** under a result, "Invite a friend" and the like are a folded row,
    open where they are the point (`/today/`).
  - **One share button per screen**, and singular and plural said right ("1 julepe").
- **A test stops it:** `node public/assets/js/fin.test.mjs`.

## C-20 · One name, inside and out

A game is called one thing, and everything says it (D-535, the owner's tenet of design and
construction): the name the player reads, and its **English version for everything internal**.
Artefactos is `artifacts`: its folder and URL (`/labs/artifacts/`), its id in the usage signal (and
in `games.js` once it leaves the lab), the keys it keeps on the phone (`juegos-de-salon:artifacts`),
its test hook (`window.__artifacts`), its lab card's ids, its CSS custom properties, its end-to-end
folder (`tools/e2e/artifacts/`), its generators and its page in `docs/games/`.

- **A new game** takes its English name everywhere from the start: no working name left inside
  (no `contraption` for Artefactos), no Spanish id beside an English folder.
- **A rename renames everything in the same PR**, inside and out: the player's name in the three
  languages, then every id, key, file, folder and test. What a phone or the database keeps under
  the old name is **carried over, not dropped**: a lab game moves its `localStorage` key once on
  load; a published game also needs its Firebase paths, rankings and panel history migrated and
  its old URL kept as a bridge (C-18), so its rename is a plan the owner approves before the PR.
- **Before this canon** the rule was that ids never change (D-192): `'ahorcado'` lives in
  `/hangman/`, `'reinas'` in `/queens/`. Those stay as they are until a PR renames that
  game on purpose, with its migration: D-192's reason (an id is stored data) is now the reason to
  migrate, not to keep a second name.

## C-21 · Every game is one more game

There is one kind of game (D-542, the owner, 2026-11-08; before it D-198). "Mini" or "short" only
says a game is quick: it is never a category inside the code, the docs or the work. Conexiones,
Reinas, Tango, Babel or Shinobi are games exactly as Ahorcado, Generala or La Copa are.

- **A change for "the games" reaches every game** in the same PR: a feature, a fix, a canon, a
  check, a design rule, a text. Never only the ones in `GAMES`, only La Copa's, or only the ones
  under `public/cup/games/`. If a game truly cannot take it, its spec says why (C-13), as any
  exception does.
- **One list:** code that walks the games walks `ALL_GAMES` (`public/assets/js/games.js`).
  `GAMES` and `SUELTOS` stay apart only because of how a game is built (its engine in its own
  folder with `rules.js`, or in `cup/games/` and played in La Copa); reach for one alone only for
  something about that build. 🤖 `all-games.test.mjs` fails on a new hand-made union of the two.
- **No word for a subset:** no doc, decision, agent or player text calls a group of them
  "minigames", "mini-games" or "Cup games" as if they were another kind; say "the games", or name
  the games. La Copa's Gran Final playing shortened versions is a mode of the cup, not a kind of
  game. Cuarto Rey's *minijuegos* (what a card orders) keep their name: they are not games of the site.
